# CoreWeave Sandboxes provider

Runs workloads on [CoreWeave Sandboxes](https://docs.coreweave.com/products/sandboxes)
through the public `coreweave.sandbox.v1.SandboxService` Connect API. The Go
clients are generated by the [Buf Schema Registry](https://buf.build/coreweave/sandbox)
and pinned in `sdk/go.mod` to schema commit `7074ae5be483` (October 15, 2026).

## Try it

The offline tests need Go 1.26.2+ and no credentials or Temporal server:

```sh
cd sdk
GOWORK=off go test ./compute/cwsandbox
```

For a live smoke test, obtain a CoreWeave API key and an organization with
Sandboxes access, following the [setup guide](https://docs.coreweave.com/products/sandboxes).
The test starts an Ubuntu container, writes a workspace file, snapshots it,
stops the original, restores a new sandbox, and verifies the file and new task
queue. It does not need a custom image or Temporal server.

```sh
export CWSANDBOX_API_KEY='<your CoreWeave API key>'
cd sdk  # from the repository root
CWSANDBOX_INTEGRATION_TEST=1 GOWORK=off go test -v -count=1 -run '^TestIntegration$' ./compute/cwsandbox
```

This creates billable resources. The test cleans up its sandboxes and snapshot;
sandboxes also have a ten-minute maximum lifetime. A failed or interrupted
creation can leave a resource behind until its lifetime expires. Check the
console for leftover snapshots after an interrupted test.

The default is serverless. For an organization with its own CKS runners, set
`CWSANDBOX_MODE=cks` and optionally `CWSANDBOX_RUNNER_IDS=runner-a,runner-b`.
`CWSANDBOX_BASE_URL` overrides the endpoint **for the smoke test**; the provider
itself uses the `base-url` configuration key.

## Register with the harness

Blank-import the provider in the host process that registers the harness worker:

```go
import _ "github.com/temporal-community/sandbox-orchestration-harness/sdk/compute/cwsandbox"
```

Inside a Temporal workflow, create a sandbox using the normal harness API:

```go
sbx, err := sandbox.NewSandbox(ctx, sandbox.Provider{
    Type: compute.ProviderTypeCoreWeaveSandbox,
    Config: map[string]string{
        "container-image":      "ubuntu:24.04",
        "command":              `["sleep", "infinity"]`,
        "workspace-path":       "/workspace",
        "max-lifetime-seconds": "3600",
    },
})
if err != nil {
    return err
}
result, err := sbx.ExecuteCommand(ctx, "echo hello > /workspace/message; cat /workspace/message")
```

Use the existing `sandbox` and `compute` imports shown in the repository
examples. The host worker needs `CWSANDBOX_API_KEY`. The provider sends it as a
Bearer token; `CWSANDBOX_API_TOKEN` is accepted as a compatibility fallback.
The API key is not copied into the container. `TEMPORAL_TASK_QUEUE` is set on
each new container, including restored sandboxes.

## Configuration

Configuration is a `map[string]string` in `compute.ProviderDetails.Config`.

| Key | Required | Description |
| --- | --- | --- |
| `container-image` | yes | Pullable OCI image containing the configured executable and `sh` for command execution. |
| `command` | yes | Long-lived entrypoint; JSON array or whitespace-separated arguments. Use JSON to preserve spaces and quoting. |
| `args` | no | Additional arguments, using the same format as `command`. Malformed JSON is rejected. |
| `mode` | no | `serverless` (default) or `cks` for the caller's own-cluster runners. |
| `runner-ids` | no | Comma-separated unique runner IDs; requires `mode=cks`. |
| `cpu` / `memory` | no | Resource requests, e.g. `2` / `4Gi`. Omitted resources use platform defaults. |
| `workspace-path` | no | Absolute scratch-volume mount and working directory, e.g. `/workspace`. Enables snapshots and harness suspend/resume. Must not be `/`. |
| `workspace-size` | no | Scratch-volume size, e.g. `10Gi`; requires `workspace-path`. Omitted size uses the platform default. |
| `max-lifetime-seconds` | no | Non-negative maximum lifetime. Omitted or `0` uses the platform default, not an unlimited lifetime. |
| `base-url` | no | API origin, default `https://api.cwsandbox.com`; do not append `/v1`. |

`profile-names` belongs to the old v1beta2 API and is rejected. It is not
silently translated into v1 placement. Configuration and resources remain
subject to the platform and runner policies.

## Lifecycle and persistence

`Start` calls `CreateSandbox` and polls `GetSandbox` until the sandbox is
running. `Stop` calls `DeleteSandbox`; an already absent sandbox is success.
`ExecuteCommand` calls `Exec` with `sh -c`, returns stdout/stderr and the exit
code, and reports output truncation as an error rather than silently returning
incomplete data. Commands can have side effects before an error is returned;
the harness may retry failed activities, so use idempotent commands where needed.

With `workspace-path` configured, snapshots capture **only that scratch volume**.
Put durable files there. Snapshots do not capture process memory, the container
root filesystem, or files outside the mount. The mount starts empty and hides
any image files at that path; keep the worker executable elsewhere in the image.
Quiesce writers before snapshotting when application consistency is required.

`Snapshot` waits for `CreateFileSystemSnapshot` / `GetFileSystemSnapshot` to
report ready and leaves the source running. `StartFromSnapshot` starts a new
container with the same provider configuration and restores the workspace
before startup. `DeleteSnapshot` calls `DeleteFileSystemSnapshot` with
`allow_missing=true`.

The harness handles suspend/resume automatically using workspace snapshots;
resuming restarts the configured entrypoint in a new sandbox. No separate
workflow fallback configuration is needed. Without `workspace-path`, snapshots
and suspend/resume are unsupported. The provider's direct `Suspend` and `Resume`
methods return `errors.ErrUnsupported` because v1 has no in-place pause/resume
RPCs.

Creation and snapshot readiness waits respect the caller's context and are
bounded at five minutes. Within Temporal activities, create and snapshot
idempotency tokens are stable across retries and distinct for each activity.
Calls outside Temporal receive a fresh token per call. A failed wait reports
the resource ID so it can be inspected or cleaned up; the resource is not
deleted while a retry may still need it.
